# AGENTS.md

Guidance for AI coding agents (Claude Code, Codex, Cursor, etc.) working in this repository. Human contributors should read [CONTRIBUTING.md](CONTRIBUTING.md); everything here applies to them too.

## Project in one paragraph

Bastion is an open-source Pomodoro timer for Windows that blocks distracting **websites** and **applications** during focus sessions, with a **strict mode** that prevents the session from being stopped early. A privileged Windows service (Rust) is the single source of truth; a desktop UI (Tauri 2 + Vue 3) and a browser extension (Manifest V3) are untrusted clients that talk to it over IPC. See [docs/architecture.md](docs/architecture.md).

## Workflow

Work happens one roadmap task at a time, in the loop defined in **[docs/workflow.md](docs/workflow.md)**: the QA engineer writes acceptance tests first, the developer implements without touching them, CI and an independent security reviewer verify, and the maintainer approves from a plain-language report. Read that document before starting any task.

In short:

1. Find the active phase and next task in [docs/roadmap.md](docs/roadmap.md) → **Current status** (respect `Depends on:`).
2. Never modify acceptance tests (`**/tests/acceptance*`) unless you are the QA engineer.
3. Nothing is done until `just check` passes, QA and security both return PASS, and the maintainer approves.
4. On approval: tick the task, update **Current status**, add a `CHANGELOG.md` entry if user-visible, add an ADR in `docs/adr/` for architectural decisions, squash-merge with a Conventional Commit referencing the task (`feat(core): add pomodoro state machine (T-1.3)`), signed off (`-s`).
5. If blocked, mark the task `[~]`, write the reason in **Current status**, and stop.

Task states: `[ ]` todo · `[~]` in progress / blocked · `[x]` done.

## Repository layout

```
bastion/
├── crates/
│   ├── bastion-core/      # Pure domain logic: model, pomodoro engine, rule matching. No OS deps.
│   ├── bastion-ipc/       # IPC protocol: message types, versioning, framing. No OS deps.
│   ├── bastion-service/   # Windows service: process blocking, persistence, IPC server.
│   └── bastion-nmh/       # Native messaging host: browser extension ⇄ service bridge.
├── apps/desktop/          # Tauri 2 app. `src/` = Vue 3 frontend, `src-tauri/` = Rust IPC client.
├── extension/             # Manifest V3 extension for Chrome and Edge (TypeScript).
├── installer/             # WiX v4 MSI sources.
├── docs/                  # Architecture, roadmap, ADRs, threat model, UI stack.
└── .github/               # CI workflows, issue and PR templates.
```

## Hard rules

- **`bastion-core` and `bastion-ipc` are pure.** No `windows` crate, no `std::process`, no network, no direct system clock. Time comes in through the injectable `Clock` trait. Both crates use `#![forbid(unsafe_code)]`.
- **The UI and the extension are untrusted.** The service validates every incoming message. No client request can shorten, pause, or cancel an active strict session, or edit the blocklist it uses.
- **`unsafe` lives only in `bastion-service/src/sys/`**, one wrapper per Win32 call, each with a `// SAFETY:` comment.
- **No telemetry.** Nothing leaves the user's machine unless a future, opt-in sync feature is explicitly enabled.
- **Don't build UI from scratch.** Check [shadcn-vue](https://www.shadcn-vue.com) first; custom components only for domain-specific pieces listed in [docs/ui-stack.md](docs/ui-stack.md). Generated `components/ui/*` files are only edited for tokens or variants.
- **No hard-coded UI strings.** All user-facing text goes through `vue-i18n` (`en` and `es` from day one).
- **Every new source file** starts with an SPDX header: `// SPDX-License-Identifier: MIT OR Apache-2.0` (or `<!-- … -->` in `.vue`/`.html`, `/* … */` in `.css`, `#` in PowerShell). Source files are code: Rust, TypeScript, JavaScript, Vue, HTML, CSS and scripts. Configuration files (TOML, JSON, YAML, dotfiles such as `.gitignore`), documentation, and files generated by tools, such as lockfiles, don't carry one.

### Writing Rust tests

The workspace lints that keep panics out of the service also apply to test code, with a few exemptions. To keep `clippy -D warnings` passing:

- Integration-test files (including `crates/<crate>/tests/acceptance_t<phase>_<n>.rs`) start with the SPDX header, then a `//!` doc comment (acceptance tests list which criterion each test covers), then `#![cfg(test)]`. The `//!` satisfies `missing_docs`; `#![cfg(test)]` lets helper functions in the file use `unwrap`, `expect`, `panic!` and indexing, as `#[test]` functions and `#[cfg(test)]` modules already can.
- Unit tests go in a `#[cfg(test)] mod tests` in the source file, except in `bastion-core` and `bastion-ipc`, where they live in a sibling file declared with `#[cfg(test)] mod tests;` (`src/engine.rs` with `src/engine/tests.rs`, `src/lib.rs` with `src/tests.rs`). `just coverage` doesn't measure files named `tests.rs`, so the 90 % covers production code only instead of counting test lines. These files start with the SPDX header and need no `//!` or `#![cfg(test)]`: they are `#[cfg(test)]` modules, so the same lint exemptions apply. The one exception is the inline placeholder test in each of those two crates' `lib.rs`, until the crate has real code.
- Don't mark items `pub` in test files; `pub` items at a test crate's root trigger `missing_docs` and `missing_debug_implementations`.
- These lints apply to all test code too; use the alternative:
  - `unreachable!` → `panic!("…")`; never commit `todo!` or `unimplemented!`.
  - `&s[a..b]` → `s.get(a..b).expect("…")`.
  - Narrowing `x as u32` → `u32::try_from(x).expect("…")`.
  - `split_at` / `split_at_mut` → `split_at_checked(n).expect("…")`.
  - `Iterator::sum` / `product` → `try_fold(0, |acc, &x| acc.checked_add(x)).expect("…")`, or a `for` loop with `+=` inside a `#[test]` function. A plain `fold(0, |acc, x| acc + x)` trips `clippy::unnecessary_fold`, which suggests the banned `sum`.
- Arithmetic (`+`, `-`, `*`, `+=`, also on `Duration`) is fine inside `#[test]` functions and closures within them. Helper functions, even in `#[cfg(test)]` code, use `checked_*` plus `expect("…")`. Literal-only arithmetic such as `25 * 60` is always fine.
- If a test genuinely needs a linted construct, opt out at the narrowest scope with `#[expect(<lint>, reason = "…")]` on the statement or test function, never `#[allow]`. The reason is mandatory, and clippy reports the `expect` once it is no longer needed.

## Commands

`just check` runs every check below, in order, stopping at the first failure, and is the single gate used by agents and CI. It runs `pnpm install --frozen-lockfile` in each frontend package first, so it also works on a fresh clone whose path is short enough ([CONTRIBUTING.md](CONTRIBUTING.md#development-setup) gives the limit), and it runs the `cargo` checks with `--locked`.

```bash
# Rust
cargo fmt --all --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
cargo deny check                       # licenses, advisories, duplicate deps

# Desktop app (from apps/desktop)
pnpm lint && pnpm typecheck && pnpm test
pnpm tauri dev

# Extension (from extension)
pnpm lint && pnpm typecheck && pnpm test && pnpm build

# Tests of the Node.js scripts
node --test scripts/check-acceptance-tests.spec.mjs

# Run the service without installing it (development)
cargo run -p bastion-service -- --console
```

`just coverage` is separate from `just check`, because it needs [`cargo-llvm-cov`](https://github.com/taiki-e/cargo-llvm-cov) (`cargo install cargo-llvm-cov --locked`). It fails if line coverage of `bastion-core` or `bastion-ipc`, each on its own, is below 90 %, and reports the desktop app's and the extension's coverage with no minimum (`pnpm test:coverage` in each package).

`just check-acceptance-tests <base>` is separate too, because it needs a base: it fails if a commit in `<base>..HEAD` changes acceptance tests (`**/tests/acceptance*`) without a subject starting with `test(`, or changes other files along with them, and it can't pass on a shallow clone. It catches accidental changes; a commit prefix proves nothing about who wrote a commit ([CONTRIBUTING.md](CONTRIBUTING.md#acceptance-tests-change-only-in-test-commits)).

CodeQL runs only on GitHub ([`.github/workflows/codeql.yml`](.github/workflows/codeql.yml)). Pin any action to a full commit hash with its version in a comment.

`lefthook` runs format and lint checks on commit; CI runs everything on `windows-latest`.
